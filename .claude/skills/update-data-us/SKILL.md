# update-data-us

## 이 함수들을 어떻게 부르나

- `us_matrix.build_base`·`us_seam.check_splits`·`us_seam.fetch_tail`·`us_seam.attach`는
  전부 파이썬 함수다(CLI 아님). `scripts/`가 `sys.path`에 있어야 한다 —
  `us_seam.py:20`이 `from canslim_lib.us_matrix import ...`를 쓴다. 실행 예(2026-09-11
  세 종목으로 전체 순서를 돌려 확인함):
  ```
  PYTHONPATH=scripts python -X utf8 -c "
  from canslim_lib import us_matrix
  import us_seam
  print(us_matrix.BASE_PATH, us_seam.TAIL_PATH)
  "
  ```
- `asof`·`codes`·`base`는 전부 뼈대 파일에서 온다:
  ```python
  from canslim_lib import us_matrix
  base = us_matrix.load_base()          # .cache/us/base.json 읽기 (없으면 1번부터)
  asof = base["asof"]
  codes = list(base["series"].keys())
  ```
  `codes`는 여기서 새로 유니버스를 세우지 않는다 — `build_base`가 내부에서 이미
  `us_loader.load_tickers(variant="base")`(기본판 — Secondary Class·ADR 제외)로
  유니버스를 확정했고, `codes`는 그 결과로 채워진 뼈대의 종목 목록이다
  (유니버스를 다시 세우는 일 자체는 아래 「안 하는 것」 참조).
- `today`는 오늘 날짜다:
  ```python
  import datetime
  today = datetime.date.today().isoformat()   # 예: "2026-09-11"
  ```
  `check_splits`의 창은 닫힌 구간이라 `until`에 오늘을 주면 오늘 난 분할까지 검사한다
  (`us_seam.check_splits` 의 docstring 이 정본). 이 창은 5단계에서 `fetch_tail`이
  붙일 범위와 같아야 한다 — 좁으면 오늘 난 분할이 검사 없이 붙는다.

## 순서

1. `.cache/us/base.json` 이 없으면 뼈대를 만든다:
   `us_matrix.build_base("2024-09-01", "2026-12-31")`
   실측(2026-09-10) 126초. 종목 4,648 · 그중 310봉을 채우는 것 4,078(87.7%).
   (옛 수 「약 7,400종목 · 약 79%」는 유니버스 규칙을 걸기 전 수였다.
   시간은 까닭이 다르다 — 「약 54초」는 재는 자리가 달랐고 자료도 옛 것이었다.
   거르면 종목이 줄어드니 거르기가 느려지는 까닭일 수는 없다.
   정본은 `docs/superpowers/specs/2026-09-10-us-sepa-skill-design.md:95-99`.
   2026-09-11 정정)
2. `asof` 날부터 오늘까지 분할을 검사한다(겹친 날은 뼈대가 이기므로 asof 당일을
   다시 봐도 무해하다):
   `r = us_seam.check_splits(codes, since=asof, until=today)`

   **얼마나 걸리나.** 2026-09-11 에 `yf.download(..., actions=True)` 묶음으로
   바꿨다(그전에는 종목마다 따로 물어 4,648종목에 26.5분). 503종목 표본 실측:
   옛 길 151.3초(종목당 0.301초) · 새 길 36.1초(종목당 0.072초) = 4.2배.
   4,648종목 환산 **약 5.6분**(표본을 재서 곱한 값이다. 전체를 돌려 잰 수가
   아니다). 묶음 크기 `us_seam.SPLIT_BATCH = 200` —
   50·200·500 셋 다 같은 분할 셋을 냈고 200 과 500 은 시간도 같았다.

   ⚠️ 그 묶음이 **못 본** 종목은 뒤에서 한 종목씩 다시 묻는다(표본에서 9.9% —
   대부분 야후에 자료가 아예 없는 상장폐지 종목). 그래서 `failed` 의 뜻은
   종전과 같다 — 「분할 없음」이 아니라 **「물었는데 답을 못 받았음」**이다.
3. `r["splits"]` 가 비어 있어도 «멈추지 않는다». 분할이 있으면 뼈대를 보정해서
   잇는다(2026-09-11 사용자 결정). 보정 자체는 5단계에서 꼬리를 받은 «뒤»에
   한다 — 「뼈대가 이 분할을 이미 반영했나」를 짐작하지 않고 «재려면» 같은 날짜의
   야후 봉이 있어야 하기 때문이다. 여기서는 목록만 들고 5단계로 간다.

   ★ 왜 바뀌었나(옛 동작은 「분할 있으면 무조건 멈춤」이었다)
     - 옛 해결책이 「Sharadar 를 다시 받아 뼈대를 새로 만든다」였는데
       **Sharadar 결제가 2026-09 로 끝난다.** 10월부터 그 길이 없다.
     - 분할 검사 창은 「뼈대 기준일부터 오늘까지」라 «날마다 넓어진다».
       그대로 두면 10월 첫 분할이 나는 날 갱신이 영구히 멈추고 후보가 9월
       자료에 언다. 실측(2026-09-11) 창 이틀에 이미 분할 셋이 걸렸다
       (CYCN·LFT·PHGE, 4,648종목 기준).
     - 「분할 난 종목만 빼고 잇는다」는 사용자가 고려했다 «버린» 길이다 —
       우량주가 액면분할하면 오히려 놓치면 안 되는 그 종목을 못 보게 된다.

4. `r["failed"]` 가 비어 있지 않으면 «그대로 멈춘다»(여기는 안 바뀌었다).
   그 종목들은 「분할 없음」이 아니라 「못 봤음」이다. 몇 개인지와 종목을 보이고,
   다시 돌릴지 사용자에게 묻는다.
5. 꼬리를 받아 → 뼈대를 보정하고 → 붙이고 → 저장한다.
   `fetch_tail` → `adjust_base_for_splits` → `attach` → `.cache/us/tail.json`

   `attach` 의 계약을 정확히 지킨다(`us_seam.attach` 의 docstring 이 정본):
   ```python
   import json

   t = us_seam.fetch_tail(codes, since=asof)   # {"series": {...}, "failed": [...]}
   # 5-1. failed 를 먼저 가린다. 비어 있지 않으면 멈추고 사용자에게 알린다
   #      (여기서도 「못 받았음」이지 「새 거래일 없음」이 아니다)
   # 5-2. 분할 보정 — 뼈대는 «메모리에서만» 고친다.
   #      base.json 은 절대 안 건드린다(덮어쓰면 다음 번에 보정이 두 번 먹는다).
   adjusted, rep = us_seam.adjust_base_for_splits(base, r["splits"], t["series"])
   print(us_seam.format_split_report(rep))   # 무엇을 고쳤고 무엇이 멈췄는지 반드시 찍는다
   # 5-3. rep["blocked"] 가 비어 있지 않으면 사용자에게 «알린다».
   #      그 종목들은 adjusted 에서 빠졌으므로 합본에도 안 들어간다.
   # 5-4. attach 에는 싸개가 아니라 "series" 만 넘긴다. 그리고 base 가 아니라
   #      «보정된» adjusted 를 넘긴다 — base 를 넘기면 보정이 통째로 버려진다.
   merged = us_seam.attach(adjusted, t["series"])
   # 5-4b. 붙이면서 «버린» 꼬리 봉을 반드시 찍는다(조용히 버리지 않는다).
   print(merged["tail_dropped"])   # n_bars·n_codes·n_overlap·codes
   # 5-5. 저장 — 제자리 덮어쓰기 금지(open(경로,"w")는 여는 순간 자른다).
   #      임시 파일에 먼저 쓰고, 다시 읽어 확인한 뒤에만 옮긴다.
   tmp = us_seam.TAIL_PATH.with_suffix(".json.tmp")
   tmp.write_text(json.dumps(merged, ensure_ascii=False), encoding="utf-8")
   json.loads(tmp.read_text(encoding="utf-8"))   # 깨진 채 옮기지 않는지 확인
   tmp.replace(us_seam.TAIL_PATH)
   ```
   `attach(base, t)` 처럼 싸개를 그대로 넘기면 `ValueError` 가 난다.
   그 관문이 있는 까닭: 싸개를 넘기면 모든 종목이 `None` 으로 떨어져
   「새 거래일 없음」(정상)과 구분이 안 되는 조용한 무동작이 되기 때문이다.

   ### 보정이 무엇을 하나 (`us_seam.adjust_base_for_splits`)

   - 가격은 분할 배수로 «나누고» 거래량은 배수로 «곱한다». 둘 다 해야
     거래대금이 보존된다. 가격만 줄이면 그 종목의 과거 거래대금이 배수만큼
     쪼그라들어 유동성 관문이 멀쩡한 종목을 잘못 떨어뜨린다.
   - 같은 종목에 분할이 여럿이면 배수를 곱해 한 번에 적용한다.
     보정 대상은 분할일 «이전»의 봉이다(분할일 당일 봉은 이미 분할 후 시세다).
   - 「뼈대가 이미 반영했나」는 «짐작하지 않고 잰다»:
     관측비 = 뼈대 마지막 종가 / «같은 날» 꼬리 종가.
     분할비율에 가까우면 보정, 1 에 가까우면 그대로, 둘 다 아니면 그 종목은 멈춘다.
     문턱은 한국 `ohlcv_matrix` 의 `REBASE_MIN_DEVIATION`·`REBASE_RATIO_BOUNDS` 를
     가져다 쓴다(검산기가 얼려 둔 값이다. 여기에 값을 다시 적지 않는다).
   - ★ 「관측비 1」이 늘 「이미 반영됐다」는 «아니다». 분할일이 뼈대 마지막 봉보다
     «뒤»인데 관측비가 1 이면 야후도 아직 환산을 안 했다는 뜻이라 두 갈래를
     가를 수가 없다 — 그 종목은 멈춘다. 실측 2026-09-11 CYCN 이 이 모양이었다.
   - 보정한 뒤 이음매가 매끈해졌는지 «다시 잰다». 통과 못 하면 그 종목은 멈춘다.
   - 멈춘 종목은 합본에서 «빠진다». 조용히 옛 값으로 남기지 않는다 —
     남기면 다음 날 가짜 계단이 그대로 붙는다. 반드시 사용자에게 알린다.

   ### 꼬리 봉을 «어느 것만» 붙이나 (`us_seam.attach`, 2026-09-11 사용자 결정)

   - 꼬리 봉 날짜가 **뼈대 마지막 날보다 뒤**면 덧붙인다.
   - 꼬리 봉 날짜가 **뼈대 마지막 날 이하**면 **버린다**. 뼈대에 이미 있으면
     겹침이고(뼈대가 이긴다), 뼈대에 **없으면** 뼈대 기간 안의 **구멍**이다 —
     구멍은 다른 벤더 값으로 **메우지 않는다**. 뼈대 기간은 Sharadar 가
     정본이고 27.4해 백테스트도 그 구멍이 있는 채로 돌았다. 메우면 그 구간만
     벤더가 섞인다.
   - 왜 생겼나: 종전 코드는 「뼈대에 없는 날」을 전부 **끝에** 덧붙였다.
     야후는 `since` 보다 앞선 봉을 실제로 준다 — 그러면 날짜가 오름차순이
     아니게 되고, 계열 자르기·`dates[-1]` 관문·RS 창·이동평균이 예외 없이
     틀린 값을 낸다.
   - `attach` 는 돌려주는 **모든** 계열이 날짜 오름차순인지 나가기 전에
     확인하고 아니면 `ValueError` 로 멈춘다. 버린 봉의 수와 종목은
     `merged["tail_dropped"]` 에 실려 나오고 stderr 에도 찍힌다.
     `n_bars`(구멍)와 `n_overlap`(겹침)은 **다른 것**을 센다.
   - 실측(2026-09-11) 503종목 표본: 구멍 0 · 겹침 436 · 비순서 0. 드문 일이다.

   실측(2026-09-11, 셋으로 돌림): LFT 보정(배수 0.1, 310봉, 이음매 비 1.0029) ·
   PHGE 그대로(Sharadar 가 이미 환산해 둠) · CYCN 멈춤(위 갈래).

## 왜 이런가

- Sharadar 결제가 2026-09 로 끝난다. 뼈대는 그때 얼고 꼬리만 자란다.
- 야후는 `Close` 를 쓴다. `Adj Close` 는 배당만큼 벌어진다.
- 겹친 날짜는 뼈대(Sharadar)를 남긴다.
- 분할 검사를 건너뛰면 이음매에서 배수만큼 가짜 계단이 난다.
  야후가 분할을 반영하지 않는 종목이 있다(표본 10개 중 2개).
  2026-09-11 실측으로 «두 벤더가 서로 다르게» 군다는 것을 확인했다 —
  같은 1대10 병합인데 PHGE 는 Sharadar 만 환산했고(야후 원시 그대로),
  LFT 는 야후만 환산했다(Sharadar 원시 그대로). 그래서 「누가 환산하나」를
  규약으로 적을 수가 없고, 종목마다 «재는» 수밖에 없다.
- 분할 검사 창은 닫힌 구간이다(`asof` 부터 오늘까지, 오늘 포함) —
  `fetch_tail` 이 끝 날짜 없이 오늘 봉까지 받으므로, 검사 창이 오늘을 빼면
  오늘 난 분할이 검사 없이 그대로 붙는다.

## 안 하는 것

- 유니버스 다시 세우기 — `us_loader.load_tickers` 가 한다
- 종목 정보 갱신 — Sharadar 가 2026-09 로 멈춘다. 미해결이 둘이다:
  ① 신규 상장이 유니버스에 안 들어온다.
  ② **스냅샷 뒤에 난 상장폐지를 상장 명부로는 못 잡는다.** 얼린 표에 그 행이
  없기 때문이다. 1단계의 상장 판정(`screen_trend_template_us.is_listed_on`)은
  얼린 `lastpricedate` 를 상한으로 «쓰지 않는다» — 쓰면 기준일이 스냅샷보다
  뒤로 가는 순간 전 종목이 미상장으로 읽혀 유니버스가 0 이 된다. 대신 거래가
  끊긴 종목은 `stale`(마지막 봉 != 기준일)과 `liveness.is_halted`(최근 5거래일
  거래량 0)가 잡는다. 그 둘은 「거래가 있었나」의 자여서 「상장 명부에 있나」와
  다르다 — 상장폐지 뒤에도 장외에서 거래가 이어지면 둘 다 못 거른다.
- 야후가 «모르는» 심볼을 다 푸는 것 — 점 심볼(`BRK.B` → `BRK-B`)은
  `us_seam.to_yahoo_symbol` 이 풀지만 그 규칙 하나뿐이다. 야후가 빈 표를 주는
  종목은 `failed` 에 «안» 들어가므로, 조회 실패가 0 이라고 해서 전 종목이
  꼬리를 받았다는 뜻은 아니다(실측 2026-09-11: 점 심볼 다섯 중 넷 왕복,
  `LGF.B` 는 야후에 아예 없다).
