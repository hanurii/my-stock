## 2. 한국 쪽 ohlcv_matrix.py 를 그대로 쓸 수 있나

절반만 쓸 수 있다. 읽는 쪽은 되고 만드는 쪽은 안 된다.

| 부분 | 무엇 | 쓸 수 있나 | 까닭 |
|---|---|---|---|
| 저장 모양 | 종목마다 `{dates, closes, opens, highs, lows, volumes, timestamps}` | **된다** | 소비자가 이 키를 그대로 읽는다 (`screen_trend_template.py:87-108`) |
| `get_series(code, days_back)` | 읽어서 잘라 주는 함수 | **거의 된다** | `days_back` 이 달력일 기준이다. 그대로 쓰면 된다 |
| `update_to_latest` | 날짜별로 받아 종목별로 뒤집기 | **안 된다** | `pdata` 를 부른다. 한국 공공데이터 API 다 |
| `_trading_days` | 영업일 목록 | **안 된다** | 같은 까닭 |
| `fill_recent_via_fdr` | 최근 며칠 메우기 | **안 된다** | FinanceDataReader 는 한국 쪽이다 |
| `_apply_adjustment` · `repair_rebase_gaps` | 수정주가 되돌리기 | **안 된다** | 한국 캐시의 리베이스 문제를 고치는 코드다. Sharadar 에는 없는 문제다 |
| `foreign_rates` | 외국인 지분율 | **없다** | 미국에 대응물이 없다. 빈 리스트로 둔다 |

모듈 590줄 중 `pdata` · FDR · 외국인 · 리베이스에 닿는 줄이 96줄이다.
바깥에서 들여오는 것은 `from canslim_lib import pdata` 하나뿐이다.

```
그러니 새로 지을 것은 만드는 쪽 하나다. 읽는 쪽 계약은 그대로 둔다.
```

## 3. 한 번 흘려 읽어 추리기 — 실측

어림을 먼저 적고 쟀다. 어림은 100~180초였고 실제는 53.3초였다.
아홉 번 중 여덟 번을 과대로 잡았다. 이번엔 낮춰 잡으라는 말을 듣고 낮췄는데도 과대였다.

| 무엇 | 값 |
|---|---|
| 읽은 파일 | `.cache/sharadar/stocks.csv.zip` · 압축 988MB · 풀면 3.2GB |
| 전체 행 | 45,317,834 |
| 남긴 행 | 1,979,932 (4.37%) |
| 종목 수 | 6,905 |
| **걸린 시간** | **53.3초** |

압축을 풀지 않고 흘려 읽었다. 날짜만 먼저 잘라 견주고,
문턱을 넘는 행만 온전히 쪼갰다. 그래서 전수 훑기(88초)보다 오히려 빨랐다.

### 크기

| 형식 | 디스크 | 쓰기 | 읽기 |
|---|---:|---:|---:|
| pickle | 115 MB | 1.6초 | 7.9초 |
| json | 89 MB | 5.1초 | 2.7초 |

메모리는 파이썬이 잡은 양으로 쟀다.

| 담는 법 | 파이썬 할당 |
|---|---:|
| 그냥 리스트 | 438 MB |
| `array('d')` 로 바꾸면 | 202 MB |

리스트로 두면 438MB 다. `array('d')` 로 바꾸면 202MB 로 절반 아래가 된다.
바꾸는 데 0.4초 걸린다.

어느 쪽이든 통째로 올려도 죽지 않는다. 원본 3.2GB 를 올리는 것과는 다른 이야기다.

## 4. 실측에서 걸린 것 둘

### 날짜 문턱에 여유가 열흘뿐이다

나는 2025-06-01 을 문턱으로 잡았다. 그러면 종목이 가진 봉이 최대 320개다.
필요한 것이 310 이므로 여유가 **10일**뿐이다.

휴장일이 몇 개 더 끼거나 창이 조금만 길어지면 모자란다.
문턱을 한 달쯤 더 앞으로 당기는 편이 안전하다. 추린 행이 늘어도 시간은 비슷할 것이다.
(그 말은 어림이다. 재지 않았다.)

### 310봉을 못 채우는 종목이 다섯에 하나다

| 무엇 | 값 |
|---|---|
| 310봉 이상 가진 종목 | 5,516 / 6,905 (79.9%) |
| 못 채우는 종목 | 1,389 |

못 채우는 까닭은 둘이다. 창 안에 상장한 것과 창 안에 상장폐지된 것이다.
어느 쪽이 몇 개인지는 안 갈랐다.

이 종목들은 조건 3에서 자동으로 탈락한다. 코드가 데이터 부족을 이미 다루기 때문이다(`trend_template.py:44-45` 가 None 을 돌려준다).
그래서 흠은 아니다. 다만 유니버스를 셀 때 분모가 무엇인지 적어야 한다.

## 이 판이 못 한 것

- 문턱을 앞으로 당기면 시간이 얼마나 더 드는지 안 쟀다.
- 종목마다 파일로 쪼개 쓰는 데 걸리는 시간을 안 쟀다. 한 덩어리로만 쟀다.
  한국 쪽은 종목마다 파일 하나인데, 6,905개 파일을 쓰는 비용은 다른 자다.
- 310봉을 못 채우는 1,389개가 신규 상장인지 상장폐지인지 안 갈랐다.
- 야후 꼬리를 어떻게 붙일지는 이 판에서 안 다뤘다. 규약은 `264` 와 `265` 에 있다.
- `timestamps` 키를 안 만들었다. 소비자가 그것도 읽는다(`screen_trend_template.py:96`).
  날짜에서 만들 수 있으나 만들지 않았다.
